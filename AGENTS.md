# AGENTS.md

Project description, quickstart and layout: see [README.md](README.md). Not repeated here.

## Agent rules

- **Minimise project allocation.** Account `tra26_aiwcas` has 5000 core-hours in total, shared by ~35 users (valid until 2026-11-04). Billing is per CPU core.
  - Prefer the login node (`lrd_all_serial` runs CPU work there) over compute jobs.
  - If a GPU is needed: debug QOS `boost_qos_dbg` (30 min max, 2 running / 4 submitted jobs per user), 1 GPU, short walltime, few cores (e.g. 8 per GPU).
- **Never edit submodule contents** (`src/anemoi-core`, `src/anemoi-datasets`). Bump pins with `git -C src/<pkg> checkout <tag>`, then stage the pointer in the parent repo.
- **anemoi-core is a monorepo with per-package tags** (`training-X`, `models-X`, `graphs-X`). Pin to the latest release tag. Current pin: `training-0.17.1` (== `graphs-0.9.8`, includes `models-0.19.0`). anemoi-datasets is pinned at `0.5.47`.
- Compute nodes have no internet: install and download everything on the login node.
- `$FAST/data/arco-it-dpc-sri/` (organizer radar data) is read-only. Do not modify it.
- **Student-facing instructions go through `source setup.sh` and `bin/aiwcas`** (`validate`, `train`, `status`, `log`, `plot`, `scoreboard`, `check`). Do not tell students to `source` env paths, register kernels, call `scripts/submit.sh`/`plot_loss.py` or `anemoi-training train --config-path` by hand; add a subcommand or a `setup.sh` step instead. Tutorial paths (`AIWCAS_ENV`, `AIWCAS_DATA`, `AIWCAS_WORKDIR`, `AIWCAS_LOGS`) are defined once, in `setup.sh`.

## Gotchas

Append new entries as `- **Short title.** What happens, and what to do.`

- **Python version.** Anemoi needs Python >=3.11,<3.14 and torch >=2.3,<2.11. System `python3` is 3.6; use `module load python/3.11.7`.
- **Do not use `cineca-ai`** (`profile/deeplrn`): its torch 2.2 is too old. No conda; Singularity exists but is not used.
- **Install order.** Install torch from the PyTorch index (`--index-url https://download.pytorch.org/whl/cu126`) before the Anemoi packages, otherwise PyPI torch gets pulled in.
- **uv cache.** `UV_LINK_MODE=copy` is required (cache and venv are on different filesystems). Keep caches out of `$HOME` (50 GB quota, backup currently suspended): `UV_CACHE_DIR=$SCRATCH/.cache/uv`.
- **No internet on compute nodes.** Login nodes have it. Pre-download everything there.
- **CUDA driver.** Driver 535.274.02 is natively CUDA 12.2; cu126 wheels work via minor-version compatibility. Verified on A100-SXM-64GB.
- **Slow imports.** Importing anemoi from a Lustre venv on the HDD pool (`$SCRATCH`) takes 30 s to several minutes. Use the shared env on `$FAST`, and its squashfs image in jobs (see below).
- **Odd versions.** `anemoi-models 0.19.0.post3` and similar are expected: setuptools_scm counts commits since the models tag in the monorepo.
- **Storage.** `$HOME` 50 GB (no backup currently); `$WORK=/leonardo_work/tra26_aiwcas` 1 TB group-shared; `$FAST=/leonardo_scratch/fast/tra26_aiwcas` group-shared; `$SCRATCH` is per-user and files older than 40 days are purged.
- **Environment location.** Students use the shared env `/leonardo_scratch/fast/tra26_aiwcas/aiwcas26/envs/anemoi` (details below). `$SCRATCH/envs/anemoi` is the old per-user editable venv, kept only as a fallback via `ANEMOI_VENV`.
- **Queue.** Booster (`boost_usr_prod`, 4xA100 64GB, 32 cores/node) is often nearly full; there is no event reservation yet.
- **Slurm output.** `scripts/smoke_test_gpu.sbatch` writes `%x-%j.out` in the submit directory, so submit from somewhere you do not mind littering.
- **`TriNodes` needs `trimesh`.** The plain `anemoi-graphs` install does not pull it in, but the default training graph (`graph: multi_scale`) uses `TriNodes`. Install it with `uv pip install "trimesh>=4.1"` (the `[tri]` extra). `healpy` (`[healpix]`) is already in the venv; `h3` (`[hex]`, for `HexNodes`) is not.
- **Graph build time is mostly imports.** On a login node, `anemoi-graphs create` for O96 + `TriNodes` r=5 takes 1.5–3.5 min wall, almost all of it Python imports from Lustre. In an already-warm kernel the same `GraphCreator(...).create()` takes about 15–25 s the first time (lazy imports) and about 5 s after that. O48 + r=4 builds in about 1 s.
- **`torch-cluster` warning.** anemoi-graphs logs that installing `torch-cluster` would speed up edge building. This is harmless; the sklearn fallback is fast enough for O96.
- **`anemoi-graphs inspect` 3D HTML needs internet in the viewer.** `graph.html` (three.js) loads its library and the Earth texture from CDNs, so open it in a laptop browser, not on the cluster. It embeds every node and edge, so a full O96/r5 graph gives about 12 MB; use a smaller graph or `--area` for demos.
- **`MultiScaleEdges(scale_resolutions=<int>)` means levels 1..r**, not 0..r as its docstring says (`list(range(1, r + 1))`).
- **Building a model outside anemoi-training.** Compose only the groups you need (`compose(overrides=["+model=graphtransformer", "+data=zarr"])` with `initialize_config_dir` on `src/anemoi-core/training/src/anemoi/training/config`), then call `OmegaConf.resolve(cfg)` before `AnemoiModelInterface(config=cfg, ...)`. Unresolved, the model's internal Hydra `instantiate` fails with `Interpolation key 'model.num_channels' not found`. The interface also needs `metadata={"metadata_inference": {"data": {}}}` and `data_indices`/`statistics` as dicts keyed by dataset name (`"data"`). `model.model(...)` and `predict_step(...)` take a dict `{"data": tensor}`, not a bare tensor.
- **CPU overrides for anemoi-models.** The default GraphTransformer backend `triton` silently falls back to `pyg` on CPU (with a warning); set `graph_attention_backend=pyg` to make it explicit. `TransformerProcessor` needs `attention_implementation=scaled_dot_product_attention` (flash-attn is GPU only).
- **`model/transformer.yaml` is incomplete in models-0.19.0.** Standalone it lacks `latent_aggregator` and the decoder `num_channels` (add `+model.latent_aggregator._target_=anemoi.models.layers.aggregator.SumAggregator` and `+model.decoders.0.mapper.num_channels=${model.num_channels}`). Its graph must have no `hidden→hidden` edges (`AssertionError: Edge attributes must be provided`); use `graph=encoder_decoder_only` or `del graph["hidden","to","hidden"]`.
- **Data vs model indices.** `IndexCollection.data.*.name_to_index` gives positions in the full dataset (e.g. 101 vars); `.model.input/.model.output.name_to_index` gives positions in the tensors the model sees (99 in / 88 out with `tp`, `cp` diagnostic). Mixing them silently picks the wrong variable.
- **NaNs and pre-processors.** `Processors` checks for NaNs only on its first call; after that NaNs pass silently and spread through the graph (one land-masked field made 75% of all outputs NaN). List the imputer *before* the normaliser in `data.datasets.data.processors` (config order = application order).
- **Small CPU models are dominated by trainable graph features.** With `num_channels=32` about 97% of the ~2.6 M parameters are the 8 trainable features per node/edge (`node/edge_trainable_parameters`) on the O96/r5 graph; the stock `graphtransformer.yaml` has ~249 M, 88% in the processor. Building it on CPU takes ~5 s and ~1 GB RAM.
- **`anemoi-training train` needs `datashader`.** The training package imports it unconditionally (via the plotting callbacks), even with `diagnostics.plot.callbacks: []`. Installed `datashader==0.19.1` (+ colorcet, multipledispatch, param, pyct) in the venv. Set `diagnostics.plot.settings.datashader: False` anyway if you keep plot callbacks.
- **MLflow offline needs `MLFLOW_ALLOW_FILE_STORE=true`.** mlflow-skinny 3.17 refuses the `./mlruns` file store ("in maintenance mode") that `diagnostics.log.mlflow.offline: True` uses. Export the variable (done in `scripts/train_tiny.sbatch` and notebook 04). Metrics then land as plain text files in `<output.root>/logs/mlflow/<exp>/<run>/metrics/` ("timestamp value step").
- **`train --config-path` must be absolute.** Hydra resolves a relative `--config-path` against the `anemoi.training.train` package ("Primary config module ... not found"). Use `--config-path $PWD/configs`. `anemoi-training config validate` accepts relative paths.
- **Hydra writes `outputs/<date>/<time>/` in the cwd** for every `anemoi-training train`. Set `hydra.run.dir` (`configs/04_tiny_train.yaml` uses `$SCRATCH/aiwcas26/training/hydra/...`) or you litter the repo.
- **`training.precision=32` fails validation.** The schema wants a string; use `32-true`, `16-mixed` or `bf16-mixed`. Good demo of a pydantic error.
- **No DDP in Jupyter.** Lightning refuses `DDPGroupStrategy` (the default, even for 1 device) in an interactive session. Override `training.strategy._target_=anemoi.training.distributed.single.SingleDeviceStrategy` (the extra DDP keys are dropped by the class). Scripts and `srun` keep the default.
- **Short GPU jobs used to be mostly startup.** With the old `$SCRATCH` venv, a 1-GPU tiny run (O96, 2.3 M params) took 5.5 min, ~3–4 min of it imports. With the shared squashfs env, startup to the first step is ~20–50 s. Training: ~1 min for 500 steps (~9 it/s); 256 channels, 8 layers, rollout 2 → ~6.5 it/s, 4 GB GPU memory.
- **Tiny sample dataset splits.** The O96 sample has 39 dates (2017-01-01T06..2017-01-10T18). `start: 2017-01-01, end: 2017-01-08` gives 31 dates = 29 training samples with multistep 2 + rollout 1; `2017-01-09..10` gives 8 dates = 6 validation samples. Every extra rollout step removes one sample.
- **Login-node CPU time limit.** Processes on the login nodes are killed (exit 137) after 600 s of CPU time (`ulimit -t 600`), counted over all threads. A CPU smoke run of several configs in one process dies; run one config per process, with `OMP_NUM_THREADS=2..4` and 2–3 steps (`scripts/check_exercises.py --cpu-steps 2`).
- **`model/point_wise.yaml` fails the schema in models-0.19.0.** Its mappers have `trainable_size` (forbidden), the processor and mappers lack `num_channels`, and the encoder/decoder datasets are `era5`/`cerra`. A YAML merge cannot delete keys, so use `defaults: - model: null` and write the whole model section out (see `exercises/A_processor_zoo/variants/point_wise.yaml`).
- **Triton graph attention works on the Booster GPU nodes.** `graph_attention_backend: triton` JIT-compiles fine on A100 (job 62116755); on CPU it falls back to `pyg` with a warning. `scripts/train.sbatch` puts the JIT cache in `$SCRATCH/.cache/triton`.
- **Hour-2 jobs are ~2 min with the shared env.** The reference runs (~6 min, ~4.7 min startup) predate it. 0/A/C solutions: 500/500/400 steps at ~9 it/s, 2.3–4.7 GB GPU memory. With 64 channels, 4 ensemble members cost almost nothing extra per training step (9.2 vs 9.5 it/s), but double the memory and slow validation.
- **Variable selection is not checked by `config validate`.** If `dataset_config.select` drops a variable named in `data.datasets.data.forcing`/`diagnostic`, validation passes and training fails after startup with `AssertionError: Data indexing has invalid entries [...]`.
- **Pasting YAML under an existing key.** Appending a second `processor:` block under `model:` gives `ConstructorError ... found duplicate key processor` (Hydra does not merge within one file). Recipes in skeletons must replace whole sections.
- **Scoreboard and curves for the room.** `$SCRATCH` is `drwx------`, so other users cannot read your MLflow files. `scripts/scoreboard.py add` copies the curves to `/leonardo_work/tra26_aiwcas/aiwcas26_scoreboard/curves/` (setgid group `tra26_aiwcas`, CSV mode 664) and appends with `flock` (Lustre is mounted with `flock`). `scripts/train.sbatch` does this automatically for successful runs.
- **Login-node memory is very slow to first-touch.** Allocating and filling a fresh 78 MB numpy array took ~10 s on a loaded login node (almost all *system* time, which counts toward the 600 s CPU limit), while reading and blosc-decoding the same chunk from Lustre took 0.05 s. Reading full CERRA dates timed at 3–8 s each there, and a naive crop script was killed after 2 min. Reuse preallocated buffers (`numcodecs` `decode(..., out=buf)`, `np.copyto`) for big per-step arrays, and do not judge GPU-node data-loader speed from login-node timings.
- **The CERRA test sample is one 78 MB chunk per date.** `cerra-rr-an-oper-0001-mars-5p5km-2017-2017-6h-v3-testing.zarr` has chunks `[1, 17, 1, 1142761]`, so `area`/`thinning`/`select` still decompress the whole field. Option B1 uses a 322 × 294 grid-index window around Italy (`scripts/crop_cerra.py`, 96 MB, `-italy.zarr` in `$WORK/a08trd25/data/anemoi/`). It keeps a 2-D `field_shape`, so `area` + `thinning` still work: anemoi-datasets applies `thinning` (which needs a 2-D field) before `area`. A 3-date sample reads in ~0.02 s.
- **CERRA vs ERA5 O96 in a `cutout`.** Same 39 dates. Only 13 shared variables: `msl, sp, t_50, t_100, tp` + 8 cos/sin forcings (CERRA has `r_*`, `sf`, `cos_solar_zenith_angle` instead of `q_*`, `insolation`, `lsm`, `z`, ...). CERRA `tp` is in kg m⁻² (mm), ERA5 `tp` in m, so the boundary ring's `tp` is 1000× smaller; harmless while `tp` is diagnostic and the loss is LAM-only. The cutout's statistics are the LAM dataset's.
- **`graph/limited_area.yaml` sets `overwrite: True`.** That rebuilds the graph on every run. Set `graph.overwrite: False` to cache it. A cached LAM graph whose data points no longer match (changed `area`, `thinning` or `max_distance_km`) fails after startup with `RuntimeError: Sizes of tensors must match ... Expected size 763 but got size 3948`. The B1 configs put thinning and resolution into the graph file name by interpolation (`${dataloader.dataset.cutout[0].thinning}`, OmegaConf list-index syntax).
- **LAM graph sizes (B1: Italy `[48,5,35,20]`, thinning 4, 300 km ring).** 3812 CERRA + 136 O96 boundary points. `LimitedAreaTriNodes` resolution 6/7/8 → 103/410/1613 hidden nodes; build 10–11 s for r6/r7 and ~60 s for r8 on the login node (without torch-cluster). Swapping the cutout order puts `thinning` on O96: `ValueError: Thinning only works latitude/longitude fields`.
- **LAM metric names.** `training: lam` still logs `train_/val_multi_dataset_loss*` (the loss is masked by `node_weights` × `output_mask`), plus `val_data_mse_inside_lam_metric/data/<var or group>/1` in *physical* units (the `all` entry is dominated by `sp` in Pa²). `training/lam.yaml` lists `metrics: [z_500, t_850, u_850, v_850]`. These are not in a CERRA cutout; B1 overrides them to `[msl, t_50, tp]`. The scoreboard labels the loss `MSE(LAM)` (from `model.output_mask` = `Boolean1DMask`), which gives B1 its own comparison group.
- **`head` in notebook shell cells.** `!cmd | sed ... | head -n 30` stores `sed: couldn't flush stdout: Broken pipe` in the output when `head` closes the pipe early. End the pipe with `awk 'NR <= 30'` instead (it reads everything).
- **MLflow 3.x agent banner.** `AnemoiTrainer` with offline MLflow prints an `INFO mlflow.agent.hint: Load the ... SKILL.md` line to stderr, with an absolute venv path. `MLFLOW_DISABLE_AGENT_HINT=1` silences it (set in notebook 04).
- **Shared student env.** `/leonardo_scratch/fast/tra26_aiwcas/aiwcas26/envs/anemoi` (symlink to the immutable build `anemoi-v1`) plus `anemoi.sqfs`. It is a relocatable venv from the hashed lock `env/requirements.txt`: PyPI anemoi releases, not editable, bytecode pre-compiled as `unchecked-hash`. Build with `scripts/build_shared_env.sh --name anemoi-vN --activate` (~10 min on a login node) and never modify a build in place. The scripts default to it; `ANEMOI_VENV` still overrides it.
- **Jobs mount the env's squashfs image with FUSE.** `scripts/anemoi_env.sh` runs `/usr/libexec/singularity/bin/squashfuse_ll <venv>.sqfs /tmp/aiwcas26-$USER-$SLURM_JOB_ID/<name>` (no container). FUSE works on Booster and on the serial/login nodes. Job `/tmp` is a per-job 10 GB tmpfs that the `srun` steps share, and the mount takes <1 s. `ANEMOI_ENV_MODE=auto|sqfs|venv` (auto falls back to the venv). `squashfuse_ll` only links zlib, and the kernel squashfs has no zstd/lz4, so images are gzip.
- **Singularity is not a good fit for the env.** SingularityPRO 4.3.1 allows setuid and kernel squashfs, but `/` as a sandbox is refused and there is no fakeroot (no subuid). A base image would also need gcc for Triton's JIT and binds of `/leonardo/prod` (module python) and `/leonardo_scratch`. Plain squashfuse_ll needs none of that.
- **Startup was the old venv, not the filesystem load.** Same node, minutes apart, 0 solution: time to the first training step was 315 s with the editable `$SCRATCH/envs/anemoi` (HDD pool), 51 s with the shared venv on `$FAST` (SSD pool), and 21 s with the squashfs. With the old venv, `import anemoi.training.train.train` spent 94 s in `torch._C` alone (paging in libtorch from HDD) and 347 s wall for 13 s CPU on login07. Warm, every variant imports in about 10 s.
- **`$FAST` beats `$WORK` for software.** `$FAST` is the `ddn_ssd` pool of `/leonardo_scratch` (`$SCRATCH` is `ddn_hdd`); `$WORK` is a separate filesystem. A cold `import anemoi.training.train.train` on login08 took 98 s from `$WORK`, 20 s from `$FAST` and 13 s from the squashfs.
- **The module python runs without `module load`.** The spack `python/3.11.7` has rpaths, and `module load` costs ~8 s in a job, so the Slurm scripts skip it. Jupyter kernels and VS Code can use `<env>/bin/python` directly.
- **`setup.sh` must be sourced, from bash.** Executed (`bash setup.sh`) it prints how to source it and exits its own process; it never calls `exit` when sourced (it `return`s, and everything runs inside a function that is unset afterwards). `-q` prints problems only (for `~/.bashrc`). It writes the kernel `~/.local/share/jupyter/kernels/aiwcas26-anemoi/kernel.json` itself (no `ipykernel install`, no Python import), pointing at the stable `envs/anemoi` symlink, so an env rebuild (`--activate`) needs no re-registration; the kernel's `env` carries the `AIWCAS_*` paths.
- **The activated venv path is the resolved one.** The relocatable venv's `activate` sets `VIRTUAL_ENV` to `realpath` (`.../envs/anemoi-v1`, not `.../envs/anemoi`). `setup.sh` compares against `realpath "$AIWCAS_ENV"` to stay idempotent and to switch terminals over after an env rebuild.
- **`aiwcas validate` is one Python process.** `scripts/validate_config.py` does a text check for `???` (instant, with each TODO's hint), then Hydra compose + `BaseSchema` (what `anemoi-training config validate` does, with an absolute config dir), then the forcing/diagnostic check: names missing from `select:`/kept by `drop:` in any split, and (for configs without `select`) names the opened training dataset does not have (e.g. `cp` in the B1 cutout). On a login node it took 4–20 s per config (`open_dataset` of the B1 cutout adds a few seconds).
- **Changing the data location.** Set `AIWCAS_DATA` in `setup.sh`. Configs and notebooks still spell out `/leonardo_work/tra26_aiwcas/a08trd25/data`; switch them to `${oc.env:AIWCAS_DATA}/anemoi/...` (OmegaConf resolves it in jobs too, since `submit.sh` uses `--export=ALL`) and `os.environ["AIWCAS_DATA"]` (the kernel sets it). A config using `${oc.env:AIWCAS_DATA}` fails to resolve in a shell where `setup.sh` was not sourced; `aiwcas` sources it itself.
- **`aiwcas` finds jobs by their log name.** Logs are `$AIWCAS_LOGS/<job-name>-<jobid>.out`; `aiwcas log`/`plot` without an id use the newest one (`plot` skips `anemoi-smoke-*`). `plot` then finds the MLflow run by its `SLURM_JOB_ID` tag anywhere under `$SCRATCH/aiwcas26`, so it also works for jobs without a log there.
- **Non-exercise configs skip the room scoreboard.** `scripts/submit.sh` sets `SCOREBOARD=0` for configs outside `exercises/` (e.g. `configs/04_tiny_train.yaml`) and names their jobs after the file. For tests, `SCOREBOARD_DIR=<dir> aiwcas train ...` (after `python scripts/scoreboard.py --dir <dir> init`) writes to a private board instead; `sbatch --export=ALL` carries it into the job.
- **VS Code workspace settings.** `.vscode/settings.json` sets `python.defaultInterpreterPath` to the shared env and prepends `${workspaceFolder}/bin` to `PATH` in VS Code terminals, so `aiwcas` works there before `source setup.sh` (it then sources `setup.sh -q` itself). Notebooks carry `kernelspec.name: aiwcas26-anemoi`; re-apply with `python scripts/set_kernelspec.py` (metadata only, keeps outputs and attachments, skips notebooks not in Jupyter's 1-space JSON layout).
